# I16. Collinear DFT+U x a group with time-reversed operations (`t_rev`)

Status: **blocked**, the refusal stays. The entry's premise does not hold: the guard is reached by no input, and the term it names is the last of five pieces of a regime this package does not have.

## What was measured

The guard at `defuqumat/scf/driver.py:Calculation._setup_hubbard` tests `t_rev != 0` on `self.symmetries`, which is always `system.symmetry_group()` (`driver.py:2866`, `:4153`, the only two assignments), and for `nspin = 2` that is `collinear_symmetries` (`system/builder.py:941`, and `:824`, `:1464` for the k-set). That function is `sgam_at_collin`'s `colin_mag = 1` branch (`symm_base.f90:765`): an operation that sends every moment onto minus itself is discarded, never kept with `t_rev = 1`, and the returned `Symmetries` has no `time_reversed` at all.

- `tests/unit/test_hubbard_collinear_trev.py::test_no_collinear_group_carries_a_time_reversed_operation`: on `h2-mirror-afm.in`, the one-species antiferromagnet where the question is not empty, the crystal group has **16** operations, **8** of which flip the staggered moment (what `colin_mag = 2` would keep with `t_rev = 1`), and the collinear group keeps **8 with `t_rev` all zero**. On each of the six committed collinear DFT+U inputs (`ni-ldau-ortho`, `ni-ldau-j0`, `ni-kind1-force`, `feo-kind1-J`, `feo-amf`, `ni10-ldau`) `t_rev` is all zero. Exact (integer counts), no sample count.
- `tests/unit/test_hubbard_collinear_trev.py::test_the_collinear_hubbard_guard_fires_on_a_time_reversed_group`: with `System.symmetry_group` monkeypatched to return the 48 operations of `ni-ldau-ortho.in` with every non-identity operation marked `t_rev = 1`, `Calculation(system, pseudos)` raises the refusal, which now names `colin_mag = 2`.

Both ran on D22 (`/l/ladovj1/w-inc-I16`, run1, see the log `/l/ladovj1/review/incompat/I16/run1.log`) beside `tests/unit/test_collinear_symmetry.py` and `tests/unit/test_hubbard_spinor.py`, with the sibling spinor branch (`si-ldau-noncol.in`, eight `t_rev = 1` operations) untouched: 26 passed, 1 failed. The one failure, `test_collinear_symmetry.py::test_the_symmetrised_run_now_reaches_the_antiferromagnet`, is not this branch's: the site moment reads 0.28974306 against the expected 0.28975412 (1.105e-5 over a 1e-5 tolerance), and the same test at master `0feb4ee` on D22 (`/l/ladovj1/w-inc-I16-base`, run2) gives the same two numbers to every printed digit. This commit changes only a message, comments and tests, so no SCF number can move.

## What is missing, and where the entry was wrong

The entry gives the missing term as "the spin-index flip of `new_ns`'s `colin_mag == 2` branch". That flip is about ten lines in `NsSymmetry.apply` (gather the other channel where `t_rev = 1`), but written alone it is dead code that cannot be validated, since nothing produces a collinear group with `t_rev`. In QE the branch belongs to `use_spinflip = .true.` (`control_flags.f90:83`, default `.false.`; `setup.f90:229-237` sets `colin_mag = 2` only then), and that regime needs, in order:

1. `collinear_symmetries` keeping the moment-flipping operations with `t_rev = 1` (`symm_base.f90:768`), behind an input flag;
2. the k-wedge treating those operations as plain rotations, without `k -> -k` (`kpoint_grid.f90:104`, `irrek.f90:171`; `system/kpoints.py:112` negates unconditionally today);
3. the density symmetriser swapping the two channels for them (`symme.f90:960-1028`), that is the magnetization odd and the charge even;
4. `becsum` and the PAW one-centre symmetrisation doing the same (`paw_symmetry.f90:130`, `:399`);
5. only then `new_ns.f90:168` (and `new_nsb.f90:192`, `new_nsg.f90:306` for the flavours).

The check the entry names, "the same cell with `nosym = .true.`, exactly", is the check of that whole regime on a one-species antiferromagnet with U, not of the Hubbard piece. A `pw.x` reference with `use_spinflip = .true.` is possible beside it (T4), and QE itself turns the regime off for `lda_plus_u_kind = 2` (`setup.f90:245`).

## User guide and README

The Limits note of `docs/guide/dft-plus-u.md` is wrong as written, since a user never meets the refusal and no collinear run needs `nosym` for it. Replace the paragraph

> A collinear DFT+U run needs `nosym` when its magnetic group has operations combined with time reversal, because these exchange the two spin channels. A spinor run (`noncolin = .true.`) does not need it.

with

> In a collinear DFT+U run the code drops the operations that reverse every moment, as in any collinear run (see the Limits note of the magnetism page), so you do not need `nosym`. The spin-flip mode of `pw.x` (`use_spinflip = .true.`), which keeps these operations and exchanges the two spin channels, is not implemented. A spinor run (`noncolin = .true.`) keeps them.

The sentence in `docs/guide/magnetism.md` ("The code drops these operations, as `pw.x` does with `colin_mag = 1`, which gives the same result at the cost of more k-points.") is correct and stays. The README feature-table DFT+U row needs no change.

# I66. Checkpoint x real-time run with the potential updated

Status: done. A run with `potential = 'hartree'` or `'hxc'` takes a `checkpoint` path,
writes its whole state after every block, and a run stopped and resumed returns the
uninterrupted current bit for bit.

## The number

Two-atom silicon of `tests/unit/test_realtime.py::_silicon` (LDA, `ecutwfc = 6`, `nosym`,
2x2x2 grid, the four lowest bands from a dense diagonalisation at the starting potential),
one-cycle `Sin2` pulse at 1e11 W/cm^2 and 1.55 eV, `dt = 0.2`, `block_steps = 100`
(six blocks), `k_batch = 2`. Three runs in one process on D22, CPU, one core: (a) the
uninterrupted run with no checkpoint; (b) the same run with `checkpoint`, stopped by a raise
right after the first block's file was written (`done == 1` read back from the file before
the resume); (c) the same call again with the same path.

- `'hxc'`: `max |J_c - J_a| = 0` exactly, `np.array_equal` true on the current, on the
  energy at every block end, on `potential_change` and on `norm_drift`, with
  `max |J| = 1.540e-3` a.u. and the potential moving by 4.8e-3 Ry. `resumed_blocks = 1`.
- `'hartree'`: the same, bit for bit, `max |J| = 1.461e-3`, potential moved by 9.0e-3 Ry.
- A `'hartree'` file handed to an `'hxc'` run is not resumed (`resumed_blocks = 0`) and that
  run equals the fresh `'hxc'` run bit for bit.
- One run, `/l/ladovj1/review/incompat/I66/harness1.log` (69 s), worktree
  `/l/ladovj1/w-inc-I66` at `94dde07`.

The control that makes the zero mean something: the same resume from a file whose `v_prev`
was overwritten with `v_now` (a checkpoint that saved one potential instead of two) reads
`max |J - J_a| = 1.83e-11` for `'hxc'` and `3.76e-11` for `'hartree'` (1.2e-8 and 2.6e-8
relative). So a checkpoint missing the second potential gives a different current, and the
exact zero is not something any resume would return. A resume that restarted from the
initial states would differ at order one after the first block.

Test: `tests/unit/test_realtime.py::test_a_self_consistent_run_resumed_mid_run_is_the_uninterrupted_one`
(slow, four `hxc`/`hartree` propagations; not timed itself, the harness with about twice
the work took 69 s on D22), the same computation as the harness
without the control. The siblings `"one of"` and `"little group"` still fire in
`test_what_the_updated_potential_refuses_is_refused_by_name` (gate; 10 passed with
`-m 'not slow'` on D22, `unit1.log`).

## Fix round: the k-chunk layout in the digest

A verifier found that the digest held `np.concatenate` of the chunk rows, which is
`0..nk-1` at every `k_batch` that divides `nk` (1, 2, 4 and `None` on this 8-point mesh),
so a file written at one `k_batch` was taken by a run at another and then crashed inside the
kept block (`ValueError: scan got values with different leading axis sizes: 8, 8, ..., 4`).
This matters in practice because the `k_batch` default follows the platform, so a file
written on a CPU and resumed on a card crashed. The frozen mode shares the line and there it
was a silent wrong answer, a `k_batch = 2` file resumed at 4 off by 2.2e-4, 17.5 per cent of
max `|J|` (verifier, `/l/ladovj1/review/incompat/I66-ver/ver2.log`). Both digests now take
`_chunk_layout(chunks)` (`defuqumat/realtime/propagate.py`), every chunk's rows and live
count, so the padded last chunk of an uneven `k_batch` is a layout of its own too. A
frozen-mode file written before this commit has another digest and is ignored, meaning the
run starts again rather than resuming.

Measured on D22 at `592240e`, worktree `/l/ladovj1/w-inc-I66-v2`, one run,
`/l/ladovj1/review/incompat/I66-r2/h.log` (81 s), same cell and pulse as below:

- the resume of the earlier round is unchanged: a `k_batch = 2` `'hxc'` file stopped after
  block 1 and resumed gives `resumed_blocks = 1` and `max |dJ| = 0.0` against the
  uninterrupted run, with the energy, `potential_change` and `norm_drift` equal;
  `max |J| = 1.540e-3`. A `'hartree'` run given the `'hxc'` file resumes 0 blocks.
- a `k_batch = 2` `'hxc'` file read at `k_batch = 1` and at `None`: `resumed_blocks = 0`
  and `max |dJ| = 0.0` against the fresh run at that `k_batch`, current and energy equal.
- frozen mode, a finished `k_batch = 2` file (`done = 4`) read at `k_batch = 4`:
  `max |dJ| = 0.0` against the fresh `k_batch = 4` run, where the old digest gave 2.2e-4.
  The `k_batch = 4` run then finds its own file and returns it bit for bit.

Gate: `tests/unit/test_realtime.py::test_the_checkpoint_digest_holds_the_chunk_length`
asserts that the frozen and the self-consistent digests differ at `k_batch` 1, 2, 3, 4 and
`None` on 8 k-points (no propagation, 0.7 s). With `_chunk_layout` replaced by the old
concatenation it fails, and it passes with the fix (both run here). The three realtime gate
files on D22 with `-m 'not slow' -rs`: 25 passed, 13 deselected, no skips
(`/l/ladovj1/review/incompat/I66-r2/unit.log`). The slow test
`test_a_checkpoint_at_another_chunk_length_is_not_resumed` does the second and third
computations of the harness.

## What was missing

The entry's term, "save every state and two potentials", is right, and it is exactly the
carry of the kept block in `propagate_self_consistent`, `(psi, v_prev, v_now)`. What differs
from the frozen mode is the unit of restart: at a frozen potential it is a finished k-chunk,
here it is a finished block of `block_steps` steps, because the density couples every
k-point. Nothing in the compiled programs changed. Added to
`defuqumat/realtime/selfconsistent.py`:

- `_save` writes the carry (one `psi<c>` per channel, `v_prev`, `v_now`), the current and
  energy recorded so far and `done`, through a `.partial` file and `os.replace`, after
  every block.
- `_restore` reads a file only when its digest matches, and casts to the fresh carry's
  dtypes so the kept block replays without compiling.
- `_signature` is the frozen digest's parts plus what moves the potential: `v_scf`, the
  mode, the corrector and the little group's operations.
- `final` and `norms` moved after the block loop (a resume with every block done would
  have hit a `NameError`); the drift is still the last block's, as before.
- `extras["resumed_blocks"]` says how many blocks came from the file.

The guard in `propagate` is deleted, and `checkpoint` is forwarded. `run_realtime`,
`run_hhg` and `Calculator.get_realtime` already forwarded it, so all three now reach it.
Not covered: `propagate_orders_self_consistent` (the perturbative orders with the potential
updated) takes no checkpoint, as before, and the frozen-mode orders do not either.

The trap-check list was run against `git diff 126d6ec..HEAD` and found nothing: every
`np.asarray`, `float` and `np.savez` in the diff is in the host-side driver loop or in the
digest, outside any traced or differentiated path, and the restored carry takes its dtypes
from the fresh one rather than from a literal. The docstring of `run_realtime`'s
`checkpoint` (`workflows/realtime.py`) now says the unit in each mode.

The file size is `16 sum_c nchunks kb nbnd_c ndim` bytes of states (the whole wavefunction
store, chunk padding included) plus two potentials of `8 nspin_mag n1 n2 n3` bytes, written
once per block (stated in the function docstring).

## The user guide and README

`docs/guide/nonlinear.md`, the Limits note of the real-time section, delete:

> With the potential updated, a meta-GGA with `"hxc"` and a checkpoint give an error.

and replace it with:

> With the potential updated, a meta-GGA with `"hxc"` gives an error. A run with the
> potential updated can also be stopped and continued from a checkpoint file. The file is
> written after each block of `block_steps` steps, and it holds all the states, so it is
> as large as the wavefunctions of the run. The run continues from the file only if
> nothing has changed, and this includes `k_batch`. If you change `k_batch`, which is set
> by `memory_mode` and is different on a CPU and on a GPU, the file is not used and the
> run starts again from the beginning.

README: the feature-table row "Real-time response to a laser pulse" (line 706) has no
checkpoint cell and no footnote about it, so nothing changes there.

# I68. Wavefunction seed held under a different pool layout: done

**The number.** The entry's check is an identity: a pooled run seeded with states held under another
pool layout must reach the same converged state as an unseeded run. Measured on D22 (CPU, one slot,
harness `review/incompat/I68/harness2.py`, worktree `w-inc-I68` at `7c3860b`, log `fix2.log`, one sample;
`fix.log` is an identical first sample) on `SILICON_8K` of `tests/unit/test_parallel.py` (Si diamond,
`ecutwfc = 12`, 2x2x2 unshifted, `nosym`, eight k-points) with two pools at `conv_thr = 1e-12`. The seed
was converged with `DEFUQUMAT_POOL_BALANCE=blocks`, so its pools held rows `[0, 1, 2, 3]` and
`[4, 5, 6, 7]`; the continuation ran under the default longest-first shares, `[0, 2, 6, 7]` and
`[1, 3, 4, 5]`, so each pool needed two rows the other one held.

- Continuation against an unseeded run in the new layout: **1.39e-13 Ry** in the total energy, in
  **1 iteration against 8**.
- The control that separates the move from the continuation itself: the same seed continued in its own
  layout gives **the same total to the last bit** (-15.614354628176415 Ry on both ranks, both arms) and
  the same largest eigenvalue difference from the seed, **1.371e-7 Ry**, also in 1 iteration. So the
  1.4e-7 in the eigenvalues is what one iteration of any continuation leaves at this threshold, and the
  move between layouts adds nothing to it. The unseeded runs in the two layouts agree to 1.8e-15 Ry and
  3.9e-15 Ry in the eigenvalues.
- The guard arm: the same harness on the base commit (`w-inc-I68-base` at `126d6ec`, `base.log`) refuses on
  both ranks, rank 0 with "this pool needs rows [6] and the seed holds 0 to 3", rank 1 with "rows [1]
  ... 4 to 7". A seed whose rows had landed on the wrong k-points would have taken about the eight
  iterations of a fresh start, not one.

The redistribution itself is checked row for row in the gate
(`tests/unit/test_parallel.py::test_a_seed_moves_between_pool_layouts_row_for_row`, three pools as threads
of one process, blocks moved into a longest-first layout of uneven costs): every pool ends with exactly
its new rows, bit for bit and in its new order; a layout every pool already covers is re-indexed after the
two small gathers with nothing else sent; and a row no pool holds is refused on every pool. The fast part
of `test_parallel.py` and `test_scf_restart.py` passed on D22 (`fast.log`, 40 passed, 6 skipped that need
the QE tree under `quantum_espresso/`, not the `DEFUQUMAT_QE_ROOT` this run set; none of them is touched
here).

**What was missing, and where the entry was right.** The entry said "redistribution of rows between
layouts", and that is what was missing. Two things about it the entry did not say. First, where the
layout can differ in one process: the pool count is fixed per process, so the case is not "a different
number of pools" (what the user guide says) but a source run whose k costs, and so whose longest-first
shares, differ from the target's (`_k_costs`, or `DEFUQUMAT_POOL_BALANCE`). A checkpoint written by any
pool count was already covered (`checkpoint.load_state(rows=...)`); this item is the in-memory seed.
Second, the move cannot live where the guard is: `starting_wavefunctions` is called once per k-chunk by
`stream_start`, and the pools hold unequal numbers of chunks, so a collective there would hang. The move
is `Pools.redistribute` (`defuqumat/parallel.py`), called once by `run_scf` under pools before the loop:
two small all-gathers tell every pool what every pool holds, and the rows then travel in rounds of
`ceil(max share / pools)` rows, so the transient is the old share, the new share and about one share in
transit, never the whole set. Host-side numpy on a `PoolStore`, nothing differentiated.

**What stays refused**, each with its test: a pool's share handed to a caller with no transport to the
other pools, a one-process `run_scf` or `starting_wavefunctions` called directly
(`tests/unit/test_parallel.py::test_a_span_from_another_pool_layout_is_refused_by_name`, message
sharpened to say only a pooled `run_scf` moves rows); and a row that no pool of the run holds
(`test_a_seed_moves_between_pool_layouts_row_for_row`, last block).

**User guide**, `docs/guide/performance.md`, "Limits" note. Replace

> A starting state (`starting_from`) whose wavefunctions were held by a different number of pools gives
> an error, so you start from its density instead, or use the same number of pools. A checkpoint does
> not have this limit.

with

> A starting state (`starting_from`) from a run with pools also works when the k-points are shared out
> differently in the new run. The states move to the pool that needs them. A starting state from a run
> with pools, given to a run without pools, gives an error. In that case you start from its density.

**README**, section "One calculation on many cores", after the sentence "A checkpoint written with pools
can continue with any number of pools.", add: "A run with pools can also start from the result of another
run with pools." The feature-table row for the k-point pools needs no change.

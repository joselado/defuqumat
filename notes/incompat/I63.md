# I63. Real-time kick after `t0` x ultrasoft or PAW

Status: done. A kick that lands on a grid point after the start now runs for an ultrasoft or
PAW dataset, on `propagate` and on `propagate_orders`; a kick between two grid points still
refuses for those datasets.

## The number

The identity of the entry's check: a kick at `t1` gives the current of a run started at the
kick, shifted in time. AlAs at the superposition of atomic charges on the two-point set of
`tests/regression/test_realtime_regimes.py` (`Gamma` and `(0.25, 0.1, -0.05)`), 10 Ry, the
occupied generalised eigenstates of the dense `H(k)`, `S(k)`, `dt = 0.05`, blocks of 20
steps. Run A has the kick at `t1 = 1.0` (step 20, so the jump is the last step of the first
block) and runs 60 steps; run B has it at `t = 0` and runs 40. One run on D22, CPU, one core
each (`/l/ladovj1/review/incompat/I63/harness-us.log`, `harness-paw.log`, harness
`harness.py` beside them).

| dataset | route | `max abs(J_A(t1 + s) - J_B(s))` | scale | ratio |
|---|---|---|---|---|
| ultrasoft `alas-epsilon-us`, ecutrho 40 | `propagate`, kick 0.01/bohr along x | 1.678e-15 | response `max abs(J_B - J_B(0))` 9.807e-05 | 1.71e-11 |
| ultrasoft | `propagate_orders`, `J^(1)` | 3.171e-14 | `max abs(J^(1)_B)` 2.930e-02 | 1.08e-12 |
| PAW `alas-piezo-tiny-paw` (`nosym` dropped), ecutrho 44 | `propagate`, kick 0.01/bohr | 1.751e-15 | response 7.928e-05 | 2.21e-11 |
| PAW | `propagate_orders`, `J^(1)` | 3.124e-14 | 2.837e-02 | 1.10e-12 |

Before the kick, `J^(1)_A` is exactly zero on both datasets, and the number of electrons
promoted out of the occupied space (`excited`) agrees to the seven digits printed (7.999658e-04
ultrasoft, 7.370496e-04 PAW). The residue is what the reasoning predicts: before the kick each
generalised eigenstate is multiplied by a number at each step, so at `t1` the two runs differ
by a phase per band and a norm loss of about 2e-11 (the printed norm drift), which is the
size of the nonperturbative ratio.

**The alternative reads differently.** The same run A with the guard lifted and nothing
else (`kick_jumps` patched to return `None`, so no jump and the kick's `strength/dt` in the
midpoint rate) stops on the norm check: "a state's norm grew to 1.00000251 after step 20"
(ultrasoft) and 1.00000209 (PAW). So the in-run jump and the corrected rate are what makes
the number; a check whose alternative also passed would not have said so. The alternative was
run on `propagate` only: on `propagate_orders` it would give a finite wrong first order rather
than a norm blow-up, and I did not measure it.

**Control at the base `126d6ec`** (`/l/ladovj1/review/incompat/I63/base.log`, worktree
`/l/ladovj1/w-inc-I63-base`): `require_a_smooth_field(si2-us, Kick(0.01, time=1.0), 0.0)`
raised "a kick after the start of the run is not implemented for an ultrasoft or PAW
dataset". So the refusal fired at the base for exactly the case that now runs.

## What was missing

The entry's term, "`_Chunk.jump` applied at a step inside the run as well as at the start",
is one of two terms, and the other one is the one that would have given a wrong number
silently. `kappa_rate` is a finite difference of `kappa_t` on the grid, so a kick landing at
`times[n]` puts `strength/dt_Ry` into the midpoint rate of step `n - 1`, and
`_Chunk.generator` feeds that rate into the `-kappadot . X` term of the augmented equation
of motion. A norm-conserving run never reads the rate, which is why the refusal was the only
thing standing between an augmented run and that term. So the fix is three pieces, all in
`defuqumat/realtime/propagate.py`:

- `kick_jumps(calculation, pulse, times)` finds each kick after the start by the comparison
  `Kick.kappa_at` makes (`times >= time - 1e-14`) and returns `jumps[n - 1] = strength *
  direction` with a flag `at[n - 1]`; `None` for a norm-conserving dataset and when no kick
  falls inside the run (so those runs compile the same program as before).
- The midpoint rate has `jumps / dt_Ry` taken out (both `_propagate_channel` and
  `orders._orders_channel`).
- `_block_function(..., jumping=True)` scans `(jumps, at)` beside the grid, and a step whose
  flag is set ends with `chunk.jump(kappa_end - jump, kappa_end, psi)` behind a `lax.cond`
  on the flag, before the step's current is taken. So the current at `times[n]` is the slope
  on the jumped states, as a run started at `times[n]` takes it. The predicate is the flag,
  never the size of the jump, because under the orders' `jvp` the primal jump is zero
  (`lam = 0`) while its tangent is not. Padded steps of the last block get zero jumps
  (`_zero_padded`), not the repeated last row `_padded` gives.

The orders route (`propagate_orders`) carries the same split, the jump scaled by `lam`.

## What still refuses, and the question it leaves

A kick between two grid points still gives an error for an ultrasoft or PAW dataset
(`kick_jumps`, "between two points of the time grid"). The norm-conserving grid moves such a
kick to a grid point by the midpoint rule (the step runs at `kappa_mid`), and an augmented run
could follow it the same way, by a jump at the start or at the end of the step. Which one is a
choice of convention, so I kept the refusal and leave the question: snap the kick to the
grid point the norm-conserving run effectively uses, or keep the error.

The potential updated in time still refuses every ultrasoft or PAW run
(`selfconsistent.require_a_potential_mode`), tested by
`tests/unit/test_realtime.py::test_what_is_refused_is_refused_by_name`.

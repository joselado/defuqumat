# I78. `rotate_moments` x crystal symmetry: done (on the group the orientation cannot break)

**The number.** Against the `nosym` run, the entry's check. Tetragonal cobalt with the coupling
(`tests/data/qe/co-tetragonal-relaxed-mae.in`, ultrasoft fully-relativistic, 3x3x2), started 45 degrees off
`c`, `rotate_moments=True, conv_thr=1e-12, torque_conv_thr=1e-9`, on D22 (worktree `w-inc-I78`, harness
`review/incompat/I78/harness.py`, log `check1.log`, one sample each, CPU, one core):

| arm | nk | group used | iterations | angle from `c` | `|torque|` (Ry/rad) | total energy (Ry) |
|---|---|---|---|---|---|---|
| `with_turning_moments()`, symmetry on | 10 | `{E, I}` | 52 | 0.0019 deg | 9.6e-10 | -74.40580330453358 |
| `nosym` | 18 | none | 53 | 0.0011 deg | 9.2e-11 | -74.40580330453363 |

The totals agree to **5.7e-14 Ry**, both runs converged, and the moments agree to 2.3e-5 mu_B in the
transverse component, which is the residual tilt the stepper may stop at inside `torque_conv_thr`. The
slow test asserts the energies at 1e-9 Ry. No timing is claimed: the two arms ran in one process and the
first one (21 s against 14 s) paid the compilation, so the time is not the k-set's.

The k-sets, asserted in `tests/unit/test_rotating_moments.py` and printed on this workstation: the
45-degree start's magnetic group has `nsym = 4` (`E`, `I`, and two operations with `t_rev = 1`) and an
8-point wedge; the easy axis's group has `nsym = 16` and a 6-point wedge; `{E, I}` gives 10, which is
`(18 - 2) / 2 + 2` with the two self-inverse points `k_z = 0, 1/2` at `k_x = k_y = 0`; `nosym` gives 18.
So the k-set of the start, which the refusal guarded against, is a wedge of a group the first turn breaks,
and it is smaller than the wedge of the group the run ends in, which is why neither end can be used.

**That the guard fired before.** At the base commit 126d6ec (`w-inc-I78-base`, `base.log`), the same
symmetric cell with `rotate_moments=True` raised "rotate_moments needs nosym = .true.: ..." with `nk 8
nsym 4`, in 2.4 s.

**What was missing, and where the entry was wrong.** The entry said "rebuilding the magnetic group and the
k-set as the moments turn". That is a different k-set at every step, and the wavefunction store, the
mixer's history, the Davidson warm start and the checkpoints all assume one fixed set, so it is a rewrite
of the loop and was not done. What was missing is the **subgroup that never needs rebuilding**: the
stepper turns every moment by one global rotation `Q`, an operation acts on an axial vector as
`det(R) R`, and it stays a symmetry of `Q m` for every `Q` only if that action commutes with all of
SO(3), so only if `det(R) R = 1`, meaning `R = E` or `R = -E` (inversion), each with any fractional
translation. The texture test is the magnetic filter's, already passed, and a rigid rotation preserves it.
Inversion is a symmetry of the coupled Hamiltonian for any moment direction, so `E(k) = E(-k)` holds along
the whole run and the wedge sum is exact, which is what the 5.7e-14 says.

Implemented as `system/symmetry.py:orientation_free_symmetries` (the filter, applied to the output of
`magnetic_symmetries`), a static field `System.turning_moments` read by `System.symmetry_group` and by
`System._respin_kpoints` (the two places that build the group for a System; `build_system` never sets it),
`System.with_turning_moments()` which rebuilds the k-points as `with_moments` does, and
`Calculator.with_turning_moments()`. The FFT grid is unchanged, since `basis/builder.py` sizes it from
`find_symmetries` and not from the run's group. `_refuse_rotating_moments` now accepts `nosym` **or** a
System with `turning_moments`.

**Decisions taken the conservative way, for the user.**

- The operations `{+-E | t}` followed by time reversal also act as a constant (`-1`) on every moment and so
  commute with `Q`; they are symmetries of every turned texture in principle, but no cell here exercised
  them under the stepper, so they are dropped. Keeping them would reduce the k-set of a PT-symmetric
  antiferromagnet further.
- The group is not chosen automatically by `run_scf(rotate_moments=True)`: the k-set is part of the
  `System`, and a Calculator whose result came from a different k-set than its own would hand downstream
  methods (DOS, response) a wedge of the wrong group. So the user asks for it with
  `with_turning_moments()`, and the refusal names the method. Question for the user: should a `&system`
  keyword set it from an input file, or should `get_scf(rotate_moments=True)` on a symmetric Calculator
  rebuild itself?
- Measured on ultrasoft cobalt only. PAW under the flag was not measured; nothing in the change is
  dataset-specific (the PAW one-centre torque is a sum over k of a per-k quantity that inversion leaves
  unchanged, and that sum already runs on symmetric verbose runs without `rotate_moments`), so no PAW
  refusal was added.

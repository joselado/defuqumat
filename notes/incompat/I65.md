The one case that does not agree is the hydrogen atom under `secant` with the target at 0.6 mu_B, and it
is not a measurement of the resume. There the moment is saturated at exactly +-1.000000000000 mu_B on
both sides of every field step, so the secant's `chi = dm/dB` is a difference of round-off and its sign
picks between the secant step and Elk's step. The two trajectories agree to the printed digits through
iteration 17, differ by 4e-6 relative in `accuracy` from 18, and at 22 one takes a step the other does
not (`harness2.log`, `h-secant-traj`). Neither run converges in 400 iterations. The `fe-fsm.in` secant
run, whose steps fall on both sides of the interruption and read the restored previous pair, is the
measurement for that update.

**What was missing, and where the entry was wrong.** The entry said "the controller's driven field in
the file". That is half of it. The field the controller changes is six leaves of `MagneticField`, now
listed once as `fields.DRIVEN_LEAVES` (`uniform`, `atomic`, and the secant's `previous_uniform`,
`previous_moment`, `previous_atomic`, `previous_site_moments`); the pools already broadcast exactly those
(`driver._DRIVEN_FIELD_LEAVES`, now an alias). The other half was on the resume side, and the file
alone would have fixed nothing: `run_scf` sets `field = calculation.magnetic_field` (the input's field,
rebuilt from `scf.in`) and its resume block restored `field_scale` only. What was implemented:

- `checkpoint.save_state` writes the six leaves as `field_<leaf>` arrays (absent means `None`), with the
  scheme and the update rule in the metadata, for a field in `FEEDBACK` only. `_refusal` now returns
  `None` and stays as the hook the pooled writer calls.
- `checkpoint.load_state` builds `SCFResult.magnetic_field` from the `calculation` it is given: the
  calculation's field with the saved leaves poured back (`eqx.tree_at`, the dtype of the input field's
  `uniform`). A field no controller drives comes back as the calculation's own field, where it used to
  come back as `None` with or without a calculation. `magnetic_field` moved from `_REFUSED` (now empty)
  to a new `_DRIVEN` list, so `unhandled_fields()` stays empty.
- `run_scf` takes the starting state's driven leaves onto its own field when that field is a feedback
  one, through one helper, `driver._carried_driven_field`, on both resume routes: the `checkpoint_dir`
  resume and an explicit `starting_from` (a `load_state(..., calculation=c)` result or another run's
  result in memory). The first version did this on the checkpoint path only, and the fix round below is
  why that was wrong.
- `workflows/relax.py`'s resume now loads `scf_state.npz` with `calculation=`. Before I65 a
  fixed-spin-moment relaxation wrote no state, so this loader never met a driven field; now it writes one,
  and a load with `system=` alone would have refused the second submission. The relaxation uses only the
  density and `becsum` of that state, since every ionic step's SCF starts from the input's field, so
  nothing else changes there. Not measured by a run (no fixed-spin-moment relaxation is in the tests).

**A behaviour change beside the item.** `load_state(..., calculation=c)` used to give `magnetic_field =
None` for every field. It now gives the calculation's field (driven leaves restored under a feedback
scheme). The consumers that read `result.magnetic_field` (`response/velocity.py`, `effmass.py`,
`magnetoelectric.py`, the transport, PDOS and STM workflows, `ultracell/driver.py:1252`) therefore see the
field a loaded state was converged under, where they silently saw none; the ultracell now refuses a loaded
reference held by a penalty constraint, as it already did for one in memory.

**Fix round (2026-10-16): the other resume route.** The verifier refuted the first version: the manual
resume that `run_scf`'s docstring advertised, `starting_from=load_state(..., calculation=c)` with
`mixing_from=dir`, still restarted the controller from the input's field without a word, since the field
was taken in the checkpoint path's resume block only and the `starting_from` branch never read it. Before
I65 that route could not be reached for a fixed-spin-moment run (`save_state` refused the file), so the
first version opened it in the P56 failure mode. Now both routes go through `_carried_driven_field`, which
pours the seed's six driven leaves onto this run's field when the run's field is a feedback one, the seed's
scheme and update rule are the same and every leaf has this run's shape, and which warns by name ("... so
the driven field is not carried over: the fixed-spin-moment controller restarts from the input's field
...") when a seed's driven field fails one of those. A continuation with `magnetization = 'seed'` or
`'none'` keeps the input's field without a warning, since it asked for the moment to start again (except on
a checkpoint resume, where that argument is refused already). The docstring's sentence "Refused, once and
by name, for a run whose field changes between iterations (`reducebf`, a fixed spin moment)", stale for
`reducebf` already, is replaced by what each route restores.

The hydrogen row is the check, and the manual route now passes it exactly. At convergence the manual route
does not reproduce the uninterrupted run, with the field carried or not, and should not be expected to: it
restores neither the iteration count, `ethr`, `accuracy` nor the occupations (`driver.py` sets
`resumed_state` on the checkpoint path only, by design), so the loop runs a fresh threshold schedule and
stops at another point inside the fixed-spin-moment tolerance, `FSM_TOLERANCE = 1e-3` mu_B. Every final
moment above is within it, and the energy differences follow from it: B times the moment difference is
0.011 Ry x 1.0e-3 mu_B = 1.1e-5 Ry for the `elk` carried arm, against the measured 1.12e-5 Ry (2.2e-6 and
2.0e-6 Ry for the others). What the carried field changes at convergence is the cost, 29 against 38
iterations under `elk` and 32 against 34 under `secant`. The density and the energy of the hydrogen row are
2.0e-6 and 1.0e-5 Ry from the uninterrupted run on both manual arms, for the same reason (the fresh
threshold), so the test asserts them loosely and the field tightly.

Open beside this, not measured and not fixed: the manual route also does not carry `reducebf`'s
`field_scale` (same mechanism, outside this item), which the docstring now says.

A further behaviour change: `Calculator.with_positions` and `with_spin` seed the next SCF through this same
`starting_from`, so a fixed-spin-moment calculator derived from another now starts its first SCF from the
parent's driven field rather than from the input's, wherever the scheme, update rule and shapes agree (a
spin promotion that reshapes the field warns and keeps the input's; `with_moments` passes `'seed'` and is
unchanged). `run_relax` is unaffected, since it hands each ionic step a density and not a result. This is
a better starting guess and the same converged state to within the tolerance above, but it is a change in
an existing path, and if you prefer the conservative form (carry the field only from a loaded checkpoint)
it is one condition in `_carried_driven_field`.

**What is refused now, each with a test that fires it** (`tests/unit/test_checkpoint.py`):

- a file holding a driven field loaded without a `calculation`, since the spheres, the targets and the
  gain are not in it (`test_a_driven_field_is_refused_without_a_calculation_to_pour_it_onto`, which also
  checks that `strict=False` warns and gives `magnetic_field = None`);
- a driven field loaded against a calculation with another scheme or update rule
  (`test_a_driven_field_is_refused_against_another_controller`, `elk` file against a `secant` input);
- a file with no driven field loaded against a fixed-spin-moment calculation of the same cell, which the
  fingerprint passes (`test_a_state_with_no_driven_field_is_refused_by_a_driven_run`);
- a driven leaf whose shape differs from the input field's (in `_restore_driven_field`; no separate test,
  since a change of `nat` or of the spin regime is caught by the fingerprint first);
- a seed whose driven field belongs to another update rule, met by an explicit `starting_from` (a warning
  by name and the input's field, `tests/unit/test_scf_restart.py::test_a_driven_field_from_another_controller_is_not_carried`,
  an `elk` result seeding a `secant` run; the same test checks that `magnetization='seed'` keeps the input's
  field with no warning). It failed on the first version's `driver.py` (no warning), `new-tests-rev.log`.

The sibling refusals of a field elsewhere are unchanged and are a different machine: the Sternheimer stack
and real-time propagation still refuse a ground state under a constrained moment
(`test_sibling_refusals.py::test_the_sternheimer_stack_refuses_a_magnetic_field`).

**User guide**, `docs/guide/performance.md`, "Limits" note, second paragraph. Delete

> The SCF does not write a checkpoint when the magnetic field comes from a
> fixed-spin-moment scheme (`constrained_magnetization = 'fsm'`,
> `'atomic fsm'` or `'atomic fsm direction'`). It says so once and runs on
> without one, because this field changes at every iteration and no input
> file says what it reached, so a restart would go back to the input field.

and replace it with

> A fixed-spin-moment run (`constrained_magnetization = 'fsm'`, `'atomic fsm'`
> or `'atomic fsm direction'`) also writes a checkpoint. This field changes at
> every iteration, so the checkpoint stores the field that the scheme reached,
> and a restart continues from that field. On bcc iron the restarted run takes
> the same 26 iterations as a run without a stop. If you load such a state
> yourself with `load_state`, you give `calculation=`, because the rest of the
> field comes from the input file.

and in `docs/guide/ground-state.md`, "Limits" note, after "A DFT+U state is saved, and its Hubbard
manifold is built again from the `HUBBARD` card when it is loaded." add

> A fixed-spin-moment state is saved with the field that the scheme reached.

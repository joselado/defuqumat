# What ten readers found in the code after the last audit, 2026-11-20

## What this is

The reading audit of 2026-11-15 (`notes/AUDIT-2026-11-15.md`) read the whole package at
commit `b5b88c5c`. Since then five pieces of work landed: the fixes of that audit (P178),
the tip orbitals in vertical transport (P179), writing a `pw.x` save directory with the
spinor DFT+U symmetrizer fix (P180, OPEN XXXI), writing an Elk state (P181) and the local
mBJ (P182). This audit reads only that new code, at commit `e22a1c5d` on branch `lmbj`.

The new code was cut into 10 slices, one reader each, all on Opus 5.5. Each reader looked
for bugs and for optimizations, and was told to quote the code path and to name an input
that reaches it without being refused upstream. There was no skeptic stage: with ten
agents, the user's number, every agent was a reader. So no finding here has been tried by
a second agent, and the severity and confidence are the reader's own.

Nothing was run, by the user's instruction ("no execution, just reading"). The 741 shell
commands in the readers' transcripts were searched afterwards for `python`, `pytest`,
`ssh` and `tools/`, and none matched. So every entry is a claim about what the source
says, not a measurement of what it computes. Three of the cited paths were read again by
hand in the main session (the natural log of the Elk core join, the cell mean of the mBJ
vacuum hold, the early return of `_turned_tips`), and each says what its entry reports.

The line numbers are those of `e22a1c5d`. If a line no longer holds what an entry
describes, grep for the symbol.

### 1. `defuqumat/io/elk_allelectron.py:374`: An unpolarized DFT+U template is not refused: its vmatmt is written beside our density and Elk uses it in the first diagonalisation

*bug, severity medium, confidence high, slice `elk-allelectron`.*

ElkState.read refuses only a spin-polarized DFT+U state (elk.py:541). all_electron_state builds the state with dataclasses.replace(base, rhomt=..., rhoir=...) and later replaces only the potentials, so base.dftu and base.vmatmt survive. write_elk_state then writes vmatmt whenever state.dftu != 0 (elk_write.py:147-149). Nothing in elk_allelectron.py or elk_potential.py checks dftu or a Hubbard term on the defuqumat side (grep is empty). In Elk 11.0.2, readstate reads vmatmt when both the run and the file have dftu != 0 (readstate.f90:251-254). gndstate.f90 then calls genevfsv in the first loop before gendmatmt/genvmatmt (lines 193-201). So the first diagonalisation uses our density's potks together with the template's U matrix. With the template the docs suggest, a run written after one loop, that matrix belongs to Elk's atomic-superposition density. PLAN P181 (2026-11-18 bullet) says 'Elk's DFT+U vmatmt ... stay refused tonight', and the cited readstate lines describe dftu = 0 on file. The code does neither. The converged answer is not affected, because Elk rebuilds vmatmt after the first loop. The start is inconsistent, though, and no test covers it.

**Reached by.** An unpolarized Elk run with dftu = 1 used as the template, for example Elk's own DFT+U NiO computed nonmagnetically, or any unpolarized dftu template. A defuqumat PAW run with or without HUBBARD on the same cell, then calc.write_elk_state(dir, template).

**Suggested fix.** Refuse base.dftu != 0, and a calculation with a Hubbard term, by name, as the record says. Or write dftu = 0 and no vmatmt record, so that Elk starts the matrix at zero (readstate.f90:251), and record the measured first residual.

**How to confirm.** Read the written STATE.OUT with ElkState.read and check that state.dftu != 0 and that state.vmatmt equals the template's byte for byte. In Elk, run task 1 with and without dftu = 0 forced on file and compare the first residual.

### 2. `defuqumat/io/elk_potential.py:1207`: The symmetrisation group is never checked against Elk's, so nosym, symtype 2 and non-primitive cells all get a group Elk did not use

*bug, severity medium, confidence high, slice `elk-potential`.*

elk_space_group keeps one fractional translation per lattice rotation (the break at line 1207, after the first b that maps the atoms) and ignores symtype. In Elk, symmetry.f90:15 sets nsymlat = 1 when symtype = 0 (nosym = .true.), and findsymcrys.f90:97 drops every translation but zero when symtype is 2. Elk's findsymcrys also calls findsym once for each candidate translation vtl, so a rotation appears once for every translation that works. In a non-primitive cell nsymcrys is therefore nrot x ntrans (for example 48 x 4 for Si in the conventional cubic cell), where the Python keeps 48. Elk prints the count in INFO.OUT ('Number of crystal symmetries', writeinfo.f90:201). read_elk_parameters does not parse it, and elk_allelectron.py:393 discards the nsym that crystal_symmetrizer returns. With nosym the written vxcmt is symmetrised where Elk's is not, and the record measured that difference on Si2 at up to 4.4e-3 Ha in the channels the site symmetry forbids. In a non-primitive cell the Python set is a set of coset representatives and not a group. It averages correctly only if the density is invariant under the pure translations. QE's sgam_at turns fractional translations off in a supercell, so that invariance holds only to SCF convergence.

**Reached by.** Any template run with nosym = .true. or symtype 0 or 2 (Si2 diamond with symtype 2 has 24 operations in Elk and 48 here), or a template on a non-primitive cell such as Si in the 8-atom cubic cell. Upstream only the lattice, the atoms and the spin regime are checked.

**Suggested fix.** Parse 'Number of crystal symmetries' in read_elk_parameters and refuse when crystal_symmetrizer's count differs. Pass symmetry=None when the count is 1, which the exchange_correlation_potential docstring already gives as symtype = 0. Keep every translation per rotation, as findsymcrys does.

**How to confirm.** Run Elk on the Si2 template with nosym = .true. and with symtype = 2, write from the same defuqumat state, and compare the written vxcmt with Elk's own potks of that density, as the record's h_sc check does. Then compare len(rotations) from elk_space_group with INFO.OUT's 'Number of crystal symmetries' on an 8-atom cubic Si template.

### 3. `defuqumat/io/qe_gvectors.py:142`: pw.x with memory='small' on more than one FFT rank reads the written density scrambled, and says nothing

*bug, severity medium, confidence high, slice `qe-save-io`.*

qe_gvector_order returns ggen's global order. pw.x calls ggen with no_global_sort = smallmem (PW/src/init_run.f90:89-90), and smallmem = (memory == 'small') (input.f90:902). In that branch each rank enumerates only its own sticks (recvec_subs.f90:140-142) and sorts them locally, and ig_l2g(ngm) = ng + ngm_offset (:238-239). So the global index is blocked by rank, and pw.x's own file is in that order (write_rhog merges by ig_l2g). read_rhog scatters the stored coefficients with ig_l2g and does not read the Miller indices when the gamma flags agree (io_base.f90:716-735, :779). A file in the global sorted order is therefore placed on the wrong G-vectors. ngm_g is the same, so the 'zero-padding' infomsg does not print. G=0 usually sits on rank 0's longest stick, so the charge stays right and nothing is renormalised. Neither the docstrings (qe_gvectors.py:1-9, qe_density.py:20-23, :561-564) nor docs/guide/qe-seed.md mention memory='small'. The reader is not affected, because it reads the Miller record.

**Reached by.** Any write_qe_save (for example Si2 PAW from the guide), then pw.x with &CONTROL memory='small', startingpot='file', run as mpirun -np 4 pw.x with one pool, so dfftp%comm has 4 ranks. The memory option is what a user sets for the large cells this writer is meant for.

**Suggested fix.** Say in the docstring and the guide's Limits note that the written file is for a pw.x run without memory='small' (or with one FFT rank). An option to write the rank-blocked order would need the stick distribution of pw.x and is not worth it.

**How to confirm.** Run pw.x 7.5 with memory='small' under mpirun -np 2 on the Si2 PAW fixture. Write the save with pw.x itself and compare its Miller record against qe_gvector_order: they should differ. Then restart that pw.x from defuqumat's folder and compare the first-iteration accuracy with the global-sort run (P180: 3 iterations from 1.4e-10).

### 4. `defuqumat/workflows/transport.py:540`: On a symmetry-reduced k-set, the per-channel maps (tip_channels=True) of pxy, p, CO and Pb are symmetrised over the group and are not the channel maps

*bug, severity medium, confidence high, slice `tip-core`.*

_turned_tips returns None when the sum over channels of c c^dagger is the same in every image (`if same: return None`, line 540). Its docstring names this case: "s, pz, the incoherent pxy". _completed_on_a_wedge (line 2118) then assembles every image with the unturned channels and sums values["channels"] over the images together with the total. The total is right, because T = tr(A sum_c c c^dagger) is invariant. Each channel on its own is not. The px channel at the image S r is |d_x psi_kw(S r)|^2 with x fixed, where the full grid has |d_{S x} psi_kw(S r)|^2. Relabelling S' = S R shows that the returned px map is invariant under the whole point group, while the real px map of a C3 or C6 crystal breaks C3 (its lobes lie along x). V9 compared totals only, and test_the_channels_add_up_to_the_map runs on a full grid. Nothing refuses tip_channels on a wedge.

### #13: the axial average of the wedge's spin moments

Bin 4, deferred, with no code changed. The identity the audit names is right for a sum: `sum_k w_k Tr[sigma_i T_n(H_k)]` over the wedge, averaged over the group the wedge was cut with in the axial representation (`det(R) R`, with a sign for every `t_rev` operation and for plain time reversal), is the whole-grid sum. Three things stop it from being an optimization with a round-off check inside fast-test cost.

1. The default trace is `"stochastic"`, and there the two routes are equal only in expectation. The wedge draws other random vectors, and fewer of them. The variance of the weighted wedge sum is `sum_k w_k^2 / R`, against `1 / (N R)` on the whole grid of `N` points, so it is larger by up to `N / nk_wedge` at equal `n_random`. At equal noise the wedge needs that many more vectors, and the recursion is not cheaper. The scalar DOS of a `spin_resolved=True` call would also move back to the wedge's random vectors. Only `trace="exact"` gains, by `N / nk_wedge` in the recursion (4 on SeI at shifted 2x2x2, up to 48 on a cubic cell).
2. On a nonmagnetic spinor, time reversal is in the grid's group, so the axial average of any `(3, N)` array is identically zero. A comparison there cannot fail. The spin DOS of a nonmagnetic run is zero by symmetry, so the cheap answer there is not an average but zero, and whether to return it without running anything is the user's choice.
3. Only a magnetic cell tests the average. It needs a group with both `t_rev` operations and improper ones, a check that dropping each sign breaks the equality, and wedge weights that are orbit sizes under exactly that group, which on a shifted mesh is `grid_stabilizer`'s subgroup. `system/wedge.py:wedge_group` refuses magnetic wedges today for the same reason: no magnetic cell has been measured against its whole grid.

The work, sized: a magnetic norm-conserving spinor cell with `t_rev` operations at a fixed density, no SCF (the SeI cell with a starting magnetization along a three-fold axis is a candidate); the average over `grid_symmetry()`, restricted to the grid's stabilizer; whole grid against wedge with the exact trace on that cell and on SeI; the two sign checks; and the timing pair after a warm-up, both arms on cores 0 to 3, in `PERFORMANCE.md`.
